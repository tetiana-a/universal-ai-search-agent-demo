# AURELIUS · ТЗ 1.2 — приёмка, развёртывание и тестовый период

Документ для заказчика: как проверить каждый критерий раздела 9, как развернуть систему у себя и что зависит не от кода.

## 1. Критерии готовности (раздел 9) и как их проверить

| Критерий | Как устроено | Как проверить |
|---|---|---|
| Бот понимает голосовые задачи и задаёт уточнения | Голос на любом языке → текст (Gemini) → ИИ-разбор в кампанию: тема, регион, языки, площадки, текст и переводы, 40 ключевых слов, смежные аудитории, расписание. Если чего-то не хватает, бот задаёт вопросы. Поиск и размещение запускаются только кнопками владельца | Отправить боту голосовое «Продаю квартиру в Валенсии…» без города → бот спросит город; ответить голосом → карточка обновится |
| База профильных и смежных сообществ по набору запросов; тематика меняется без кода | Кампания ищет по своему списку слов (до 40), своим запросам `/cq`, со смежными аудиториями (барахолки, экспаты, районы). Результаты объединяются без дублей. У каждого сообщества: 🟢 профильное / 🟡 смежное и «по какому запросу найдено». Исключения: `/cx` | Создать две кампании на разные темы (недвижимость и ретриты) — обе работают без правок кода |
| Полнота ≥ 90% | Команда `/recall <id> <ссылки>` (или `POST /api/campaigns {action:"recall"}`). Бот проверяет живость каждой ссылки из ручного списка, считает долю живых, уже найденных ботом, добавляет недостающие в базу и превращает их названия в новые поисковые запросы (самообучение) | Заказчик вручную находит 20–50 сообществ по той же теме и региону → `/recall` → процент. Если меньше 90% — «🔎 Искать ещё» и повторить `/recall` |
| В базе нет неактивных без пометки | Каждая запись имеет статус активности: «активна», «неактивна — исключена из размещения», «не проверено (нет публичной ленты)». Порог: дата последнего поста и частота, меняется командой `/activity 30 0.5`. Проверка повторяется ежедневно | Excel/CSV, колонка «Активность»; `/activity` |
| Публикации по расписанию в заданном объёме, без блокировок 14 дней | Ежедневный план: цель в день (по умолчанию 300) делится между площадками с разрешением (бот в Telegram, партнёры, ручная очередь), не больше лимита группы в день, интервал между постами, без дублей. Расписание: `/schedule <id> 9,13,18 будни до 31.12`. Бот публикует в свой час | Отчёт `/creport`, журнал публикаций в Excel/CSV |
| Мониторинг и ежедневные отчёты | Каждый день: проверка живости → план → задания партнёрам → публикации → мониторинг запущенных кампаний → отчёт в Telegram. Мониторинг ищет посты по ключевым словам, типу и цене (`/cwatch <id> квартира, дом 100000-300000`), считает просмотры и реакции, присылает самые вовлекающие посты с автором | Отчёт приходит в группу каждый день около 09:00 (Мадрид) |

## 2. Что зависит не от кода

1. **300 размещений в сутки** — арифметика площадок. При лимите 3 поста в группу в день и интервале 1 день нужно не меньше 100 площадок с согласием админов (бот добавлен в Telegram-группу, админ-партнёр или своя страница). При интервале 2 дня — около 200. Команда `/capacity` показывает текущую ёмкость и сколько не хватает до цели.
2. **Полнота 90%** измеряется только по ручному контрольному списку заказчика (критерий так и сформулирован). Без списка процент посчитать нельзя.
3. **14 дней без блокировок** — это живой тест. Система не использует фермы аккаунтов, обход блокировок и автопостинг с личных аккаунтов: публикует только бот там, где его добавили админы, партнёры по договорённости и свои страницы через официальные API. Это и есть защита от блокировок.
4. **Закрытые сообщества Facebook и Instagram/TikTok** не показывают ленту без входа, поэтому их активность помечается «не проверено», а не угадывается.

## 3. Протокол тестового периода (14 дней)

1. День 0: создать кампанию голосом, утвердить слова, найти сообщества, выполнить `/recall` по ручному списку (цель ≥ 90%).
2. Разослать админам предложения (черновики на странице «Группы»), подключить бота и партнёров, пока `/capacity` не покажет устойчивую ёмкость ≥ цели.
3. Задать расписание `/schedule`, нажать «▶️ Запустить размещение».
4. Дни 1–14: каждый день проверять отчёт: размещено, отклонено, ошибки, блокировки (бот удалён из группы). Цель: блокировок 0, объём ≥ цели.
5. День 14: выгрузить журнал размещений (Excel/CSV) и отчёт.

## 4. Развёртывание

Система — одно приложение Next.js на Vercel (бесплатный тариф подходит) + база Upstash Redis + Telegram-бот.

1. Форкнуть репозиторий на GitHub, на vercel.com: **Add New → Project → Import** этот репозиторий.
2. Upstash: создать бесплатную базу Redis, скопировать REST URL и токен.
3. В Vercel → **Settings → Environment Variables** добавить:

| Переменная | Зачем |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен бота от @BotFather |
| `TELEGRAM_CHAT_ID`, `TELEGRAM_ALLOWED_CHAT_IDS` | группа управления и кто может командовать |
| `SCOUT_REPORT_CHAT_ID` | куда слать ежедневный отчёт |
| `TELEGRAM_WEBHOOK_SECRET` | защита вебхука |
| `SCOUT_ADMIN_KEY` | ключ входа в панель и API |
| `CRON_SECRET` | подпись ежедневных и ежечасных запусков |
| `UPSTASH_REDIS_REST_URL`, `UPSTASH_REDIS_REST_TOKEN` | база данных |
| `GEMINI_API_KEY` | бесплатный ИИ: голос, разбор задач, поиск Google |
| `CAMPAIGN_AUTOPOST=on` | включает публикации бота (без неё бот только планирует) |
| необязательно: `APIFY_TOKEN`, `DATAFORSEO_LOGIN/PASSWORD`, `TGSTAT_TOKEN`, `POSTIZ_API_KEY`, `JINA_API_KEY` | дополнительные источники поиска и публикации на своих страницах |
| необязательно: `INACTIVE_DAYS`, `MIN_POSTS_PER_WEEK`, `DAILY_TARGET`, `SCHEDULE_TZ` | значения по умолчанию: 30 дней, 0,5 поста в неделю, 300, Europe/Madrid |

4. **Deploy**. Затем открыть `/scout`, ввести ключ и нажать «Подключить бота» (вебхук, команды, описание).
5. Ежечасные публикации по расписанию: в GitHub → **Settings → Secrets and variables → Actions** добавить секрет `CRON_SECRET` (то же значение, что в Vercel). Файл `.github/workflows/campaign-dispatch.yml` уже в репозитории. Без него бот публикует раз в день в 08:00 UTC.
6. Добавить бота админом в свою группу управления, написать `/start`.

Все ключи хранятся только в переменных окружения Vercel (зашифрованы), в коде и базе их нет. Все действия пишутся в журнал (`/api/scout/state`, раздел «Журнал»). Остановка всего одной командой: `/cstop all`.

## 5. Где хранятся данные и где их смотреть

| Что | Где хранится | Где смотреть |
|---|---|---|
| База сообществ, кампании, задания, журнал публикаций, мониторинг, журнал действий | Upstash Redis (облачная база, данные в ЕС/США по выбору при создании) | Сайт: «Группы», «Аналитика»; бот: `/campaigns`, `/creport`; выгрузка Excel/CSV (`/export`) |
| Ключи доступа (Telegram, Gemini, Apify, DataForSEO, Postiz) | Переменные окружения Vercel (зашифрованы) | Vercel → Settings → Environment Variables |
| Ошибки работы | Журнал функций Vercel + сообщение «⚠️ Ежедневный запуск: ошибки» в Telegram | Vercel → Logs; группа отчётов |
| Код и документация | GitHub | репозиторий |

Надёжность: запросы к базе и к Telegram повторяются при временных сбоях (сеть, 5xx, лимит Telegram 429 с ожиданием `retry_after`). Если база недоступна, шаг останавливается с ошибкой, а не работает с пустыми данными, поэтому повторных публикаций в ту же группу не бывает. Каждый шаг ежедневного запуска независим: сбой одного не останавливает остальные, владелец получает одно сообщение со списком ошибок.

Рост: Redis подходит для десятков тысяч записей. Когда журнал размещений перевалит примерно за 50 000 записей (около 6 месяцев при 300 в день), правильный шаг — перенести историю в PostgreSQL (Supabase или Neon, есть бесплатные тарифы), оставив Redis для оперативных данных. Раз в месяц рекомендуется сохранять выгрузку Excel как архив.

## 5а. Архив в Supabase (PostgreSQL)

Redis хранит оперативные данные, а Supabase — полный архив всего: сообщества, кампании, задания, журнал публикаций, мониторинг, поиски, журнал действий. Каждая запись хранится одной строкой таблицы `aurelius_archive` (раздел, ID, день, данные), повторная синхронизация обновляет строку, а не создаёт дубль.

Подключение (один раз, бесплатно):
1. supabase.com → **Start your project** → войти через GitHub → **New project**: имя `aurelius`, пароль базы (сохранить), регион **Central EU (Frankfurt)** → **Create new project**.
2. Слева **SQL Editor** → **New query** → вставить содержимое файла `supabase/archive.sql` → **Run**.
3. **Project Settings → API**: скопировать **Project URL** и ключ **service_role** (secret, не anon).
4. Vercel → **Settings → Environment Variables**: `SUPABASE_URL` = Project URL, `SUPABASE_SERVICE_ROLE_KEY` = ключ service_role (Production и Preview) → **Deployments → Redeploy**.

Как работает:
- Автоматически: каждый день в ежедневном запуске (08:00 UTC) все данные переносятся в Supabase.
- Вручную: страница «Аналитика» → блок «Архив Supabase» → **Перенести сейчас**.
- Скачать: там же выбрать даты и раздел → **Excel** (лист «Сводка» + отдельный лист на каждый раздел, русские заголовки, цветные статусы) или **CSV**.
- API: `POST /api/archive` — синхронизация, `GET /api/archive?format=xlsx&from=2026-11-01&to=2026-11-30` — выгрузка (ключ `x-scout-key`).

Безопасность: в таблице включён RLS без политик, поэтому читать и писать может только сервер с ключом service_role. Ключ хранится только в Vercel.

## 6. Команды бота (кратко)

`/campaign` или голосовое — новая кампания · `/campaigns` — список · `/keywords`, `/cq`, `/cx` — слова, запросы, исключения · `/schedule` — расписание · `/cwatch` — параметры мониторинга · `/recall` — проверка полноты · `/activity` — порог активности · `/capacity` — ёмкость · `/creport` — отчёт · `/export` — Excel + CSV · `/cstop <id|all>` — стоп.
